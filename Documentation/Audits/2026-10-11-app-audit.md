# NotchShot code and responsiveness audit — 11 October 2026

The review found concrete correctness, privacy, and responsiveness failures and repaired them in the working checkout. Screenshot framing/byte fitting, privacy-indicator OS queries, and cold call-icon lookups now run off the main actor. The final candidate passed 995 tests and was built, signed, and reopened successfully. The checks establish the repaired contracts; they do not establish that every interaction, call app, display arrangement, or OS integration is now free of lag.

## Scope and acceptance

- Inventory the entire Swift source tree, trace the major product flows, and give each feature group a disposition.
- Repair confirmed defects while preserving capture pixels, export limits, user files, permissions, accessibility behavior, and existing dirty work.
- Verify risky branches with focused regression tests, run the broader suite and repository gates, build the optimized signed app, and measure the selected responsiveness change.
- Stop after those checks and the report. Keep unmeasured performance leads and optional cleanup separate from confirmed repairs.

The starting checkout was already extensively modified. The initial tracked diff, status, and 299 source/test/script hashes were saved before changes. The first batch changed 13 of those existing inputs and added a dispatcher, benchmark, and four regression-test files. The continuation also repaired application commands and call-control presentation, removed a private unused helper, and added two focused regression tests; before-images of these continuation files were retained separately. Existing edits elsewhere were preserved. No commits, pushes, deployments, external messages, real bucket uploads, or permission changes were made.

The final inventory contains **222 Swift source files, 202 in NotchShotKit, and about 73,500 source lines**. Review combined architecture and lifecycle tracing, targeted reads, repository-wide searches, two independent subsystem reviews, and automated checks. This was a subsystem audit rather than a claim that every line or visible interaction was manually exercised.

## Responsiveness measurement

The reproducible harness is [RecipeResponsivenessBenchmarks.swift](/Users/vibex/Documents/NOTCH/Sources/NotchShotBench/RecipeResponsivenessBenchmarks.swift:8). It compares the synchronous recipe/byte-fit path with the serial worker in the same optimized executable, using fresh deterministic 3456 × 2234 inputs. It queues an unrelated main-actor task immediately before processing and measures how long delivery waits, plus processing elapsed time.

The workloads are Standard, GitHub Issue framing, App Store framing, and a custom 600 KB PNG limit. Each process uses two warmup iterations and nine recorded iterations per workload. Three independent baseline/worker process pairs run in alternating order: 27 samples per workload per mode. First-iteration PNG bytes must match the synchronous reference exactly; dimensions, scale/source rectangle, and actual byte ceilings are asserted before accepting a run.

Acceptance was set before successful measurements: at least 80% lower median main-actor delivery delay for heavy recipes; processing median may increase by at most the greater of 25% or 20 ms. The cheap Standard path is a control. These measurements describe UI-thread availability during recipe work, not ScreenCaptureKit latency, cold launch time, animation FPS, or end-to-end capture completion.

| Recipe | UI-task delivery median, synchronous → worker | Processing median, synchronous → worker |
|---|---:|---:|
| Standard control | 0.025 → 0.017 ms | 0.010 → 0.024 ms |
| GitHub Issue | 139.108 → 0.025 ms | 139.089 → 115.987 ms |
| App Store | 207.280 → 0.023 ms | 207.262 → 159.105 ms |
| Custom 600 KB PNG | 53.602 → 0.024 ms | 53.587 → 60.484 ms |

All heavy recipes meet the main-actor-delay criterion (99.96%–99.99% lower aggregate medians), and all workloads meet the processing guardrail. The bounded PNG workload takes about 7 ms longer in aggregate while allowing the UI task to run immediately. Standard adds about 0.014 ms of processing overhead. Processing timings varied between processes; the robust conclusion is removing the large synchronous main-actor block, not a guaranteed reduction in total capture latency. Per-run medians and all 216 samples are retained in the evidence directory.

Two unsuccessful attempts are retained separately: an early build overlapped source edits and is invalid; the first timing fixture used a 120 KB ceiling that could not be achieved within the existing bounded encode attempts. The corrected fixture uses 600 KB. Neither failed attempt contributes timing claims, and the production encoder's limits were preserved.

## Unused code and structural red flags

1. **Unused private helper removed:** `AIHookInstaller.containsNotchShotCommand` occurred only at its private declaration and duplicated a predicate around the still-used `notchShotCommand`. It was removed in the continuation, with hook configuration tests passing. This is bounded source cleanup; no runtime speed benefit or whole-program dead-code certification is claimed.
2. **Public/legacy compatibility code needs care:** one-activity context paths, public rendering/service methods, enum cases, AppIntent types, hook handlers, and serialized model fields cannot be deemed unused just from absent direct calls. Legacy-context expiry was repaired rather than deleting that supported mode.
3. **External call-state acknowledgement remains unavailable:** the coordinator still retains legacy toggle bookkeeping, but F13 removes it from visible mute/camera state claims. Neutral toggle buttons do not imply that the app has read the call provider's actual state. PID-safe shortcut delivery and actual provider acknowledgement are separate contracts.
4. **Call-related main-thread OS work repaired in final remediation:** the original monitor synchronously registered listeners, enumerated hardware/processes and resolved client bundles on the main actor. Five optimized, alternating fresh-process probes with AppKit initialized and one active microphone client measured a 420.718 ms median blocking startup snapshot. A dedicated serial worker now owns the same operations; FIFO publications reach main with lifecycle generation guards. The same work's completion remains comparable, without polling, debounce or dropped events. See the final remediation section below.
5. **Cold startup still needs a representative profile:** [AppCoordinator.start](/Users/vibex/Documents/NOTCH/Sources/NotchShotKit/App/AppCoordinator.swift:157) performs directory/retention/orphan cleanup and starts several services; observable stores also load around initialization. These are candidate costs with a large real library, not measured launch regressions. Existing history search/path/thumbnail caches and detached writes were preserved.
6. **Broad monolithic target:** 202 library files share one target and a large main-actor coordinator. This increases coupling and can obscure blocking work. A target/state refactor is optional architectural work; it would require feature parity checks and is not a prerequisite for the repaired screenshot path.
7. **Platform integration risks remain:** MediaRemote, notification mirroring, lock/OSD behavior and some hardware controls depend on private/undocumented OS behavior. Source/tests cannot guarantee future OS compatibility. The app is directly distributed and deliberately unsandboxed; release-signing/notarization remain separate from this local Apple Development build.
8. **Compiler warning:** optimized compilation reports a pre-existing deprecated `String(cString:)` array conversion in PrivacyIndicatorMonitor. It is a maintenance item, not evidence of a runtime failure or of the reported lag.

## Research basis

Apple recommends identifying hangs/hitches using representative Instruments traces and moving lengthy work off the UI thread. That supports the screenshot worker approach, while leaving call-specific causality to actual measurements: [Improving app responsiveness](https://developer.apple.com/documentation/xcode/improving-app-responsiveness), [Ensuring work executes in a background thread](https://developer.apple.com/tutorials/instruments/ensuring-work-executes-in-a-background-thread), and [SwiftUI performance tooling](https://developer.apple.com/videos/play/wwdc2025/306/).

The LocalSend task-delegate concern was not promoted to a confirmed defect: Apple's task-specific-delegate precedence documentation supports the design, while a real receiver/callback integration remains untested. See [Use async/await with URLSession](https://developer.apple.com/videos/play/wwdc2021/10095/).

### Call-icon rendering repair and rejected layout experiments

F18: The first call-card render synchronously queried LaunchServices and loaded its app icon inside `IslandCallAvatar.body`. A sampled cold expansion included 15 main-thread samples in that cache/lookup path. The view now reads only main-actor cache/state. A serial user-initiated resolver performs the OS lookups, copies the full `NSImage` before transfer, and publishes without further worker access. Per-bundle in-flight tasks deduplicate requests; individual view cancellation leaves shared work intact. Bundle-keyed view tasks reject obsolete completion. All image representations and the existing per-process missing-app cache are preserved.

Apple explicitly permits both lookup APIs from any thread: [application URL lookup](https://developer.apple.com/documentation/appkit/nsworkspace/urlforapplication(withbundleidentifier:)), [app icon lookup](https://developer.apple.com/documentation/appkit/nsworkspace/icon(forfile:)). This supports the worker placement; it does not establish a numerical call-animation speedup.

Settings layout was investigated using actual `SettingsView` in optimized native probes. Apple documents that [fewer hosting-view sizing options can reduce layout measurements](https://developer.apple.com/documentation/swiftui/nshostingview/sizingoptions). A direct empty-sizing-option trial lost the native minimum size and was rejected. Minimum-only and explicit-container variants did not establish a reliable improvement; compile contention invalidated the wall-time comparisons. Five balanced fresh-process pairs measured median thread CPU of 1071.234 ms for the original hierarchy and 1061.936 ms for the container experiment, less than a 1% difference, without established visual parity. Every production sizing experiment was reverted. The Settings view, hosting hierarchy, minimum size and animations retain their original contract. The menu deferral experiment was also reverted because the trace did not demonstrate that it eliminated the cold Settings hitch. No cache prewarming, hidden skeleton, removed animation, or reduced export fidelity was used to manufacture a result.

The residual first-Settings hitch remains a measured performance lead with platform layout/window stacks; its exact application cause is unconfirmed. No claim of eliminating every hang, or of improved FPS across every call provider, is made.
